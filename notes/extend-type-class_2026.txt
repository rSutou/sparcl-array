Extending Sparcl with type classes (on top of rank-2 type checking)
===================================================================

Design
======

Instances are passed as implicit instance arguments (as in Agda / Lean),
not as Haskell-style class constraints (`Eq a => ...`).

- A class is an ordinary type constructor (the type of its dictionary),
  so `Eq a` is just the type `TCon Eq [a]`.
- An instance argument is written with double braces: `{{Eq a}} -> t`.
- The arrow of an instance argument is always unrestricted (Omega).
  `{{C}} -o t` or `{{C}} # p -> t` is not allowed.
- Instance arguments cannot be named inside types (no `{{eq : Eq a}}`).
  A name can be given in a definition by the pattern `{{eq}}`.
- Omitted instance arguments are inserted based on types (as in Agda / Lean).
  Explicitly given instance arguments are marked syntactically (`f {{e}}`).
  Type-directed guessing alone is ambiguous, e.g.

    sig f : {{Eq a}} -> Eq a -> a -> Bool
    def g = f eqNat     -- f {{eqNat}} : Eq Nat -> Nat -> Bool
                        -- or f {{search}} eqNat : Nat -> Bool ?

  and an argument whose type is still a meta variable (`def h d = f d`)
  cannot be classified at that point.


Concrete syntax
===============

Class declaration
-----------------

```
class C a1 ... an [extends S1, ..., Sm] [where ... end]
```

- The body may contain method signatures (`sig`) and default method
  definitions (`def`).
- Superclasses are fields of the class (as Lean's `extends`), so an
  `{{Ord a}}` argument also provides `Eq a`.

```
class Eq a where
    sig (==) : a -> a -> Bool
    sig (/=) : a -> a -> Bool
    def (/=) x y = not (x == y)      -- default method
end

class Ord a extends Eq a where
    sig compare : a -> a -> Ordering
end
```

Instance declaration
--------------------

```
instance [x :] ty [where ... end]
```

- The instance name `x` is optional. Unnamed instances are expected to get
  generated names (e.g. `instEqInt`).
- `ty` is parsed by `typeExpr`; free type variables are quantified by
  `introForAll` (same as `sig`). Instances that need other instances take
  them as instance arguments.

```
instance Eq Int where
    def (==) = eqInt
end

instance eqNat : Eq Nat where ... end

instance eqList : {{Eq a}} -> Eq (List a) where ... end
-- parsed type: forall a. {{Eq a}} -> Eq (List a)

instance {{Eq a}} -> {{Eq b}} -> Eq (Pair a b) where ... end
```

Instance arguments in types, expressions and patterns
-----------------------------------------------------

```
sig elem : {{Eq a}} -> a -> List a -> Bool       -- type
def t = elem {{eqNat}} Z Nil                     -- explicit passing
def t' = sort {{ordList {{ordNat}}}} xs          -- nested
def notElem {{eq}} x xs = not (elem {{eq}} x xs) -- binding by pattern
```

Examples are in `Examples-Class/` (moved out of `Examples/` so that
`cabal test` does not try to type-check them). All of them parse except
`Functor.sparcl`, since the type parser does not accept applications of
type variables (`f a`).


Representation (Surface.Syntax)
===============================

- `TConstraint`: removed the `TyClass` constructor (classes are no longer
  constraints). Also removed the unused `TyCl` type.
- `Ty`: no new constructor. `{{C}} -> t` is `TCon nameTyInstArr [C, t]`
  (binary, no multiplicity). `isTyInstArr` checks the name, like `isTyArr`.
- `Exp`: `InstArg e` marks an explicitly passed instance; `f {{e}}` is
  `App f (InstArg e)`. (Rejected alternative: a separate `AppInst` node.)
  REVISED 2026-11-04 (during the type-checking review, H-1; plan (c), not
  implemented yet): the constraint "`{{e}}` appears only as an argument
  of an application", now enforced by renaming (`Renaming.hs:130-138`),
  is expressed by the data type:
    data Arg p = ExplicitArg !(LExp p) | InstArg !(LExp p)
    | App !(LExp p) !(Arg p)        -- `InstArg` is no longer an `Exp`
  Why (c) rather than (b) `AppInst !(LExp p) !(LExp p)` or (a) as now:
  a spine is `(LExp p, [Arg p])` with the same `Arg` (D-1's
  `Explicit e` / `Inst e` are its constructors; flattening just collects
  the arguments of `App`s), inserted applications are
  `App f (InstArg (InstHole ref))` like user-written ones, rebuilding is
  `foldl App`, and renaming, desugaring (dictionaries are ordinary
  arguments at run time) and printing each have one `App` case with a
  helper for `Arg` (`argExp`, `mapArg`, `pprArg`); (b) splits every one
  of them in two. Cost is small: surface `App` occurs at about 10 places
  (Syntax definition / printing, `lapp` in the parser, two renaming
  cases, `go (App ..)` in typing, desugaring of `App`, of `Let1` and of
  `revdo`), none in tests or benchmarks.
  Changes when implemented: the parser reads the head by `simpleExpr` and
  arguments by `InstArg <$> instBraces expr <|> ExplicitArg <$>
  simpleExpr`, folding with `App` (`instArgExpr` leaves `simpleExpr`), so
  `{{e}}` elsewhere is a parse error (a dedicated message may be added);
  `Arg` has no `Loc` of its own (the braces' position is lost, minor);
  renaming has one `App` case (the `InstArg` error goes away);
  desugaring of `Let1` / `revdo` builds `App f (ExplicitArg e)`; D-1
  (spine arguments are `Arg`), D-3 (`Op` rebuilt with `ExplicitArg`), F-1
  / F-3 (shape of inserted applications) and H-1 (no `InstArg` case in
  `checkTy`) follow; CLAUDE.md is updated.
- `Pat`: `PInst p` for `{{p}}`.
- `TopDecl`:
    DClass !(XTId p) ![XTId p] ![LTy p] !(Decls p (LDecl p))
      -- class name, type parameters, superclasses, body
    DInst !(Maybe (XId p)) !(LTy p) !(Decls p (LDecl p))
      -- instance name, instance type, body
  Class names and parameters use `XTId` (type-level names, which stay
  `Name` after type checking), while the instance name uses `XId`
  (a value, which carries its type after type checking).


Other changes
=============

- Name.hs: added `NInstArrow` (pretty-printed as `{{->}}`) and
  `nameTyInstArr`.
- Parser/Id.hs: added `class`, `instance` and `extends` to `keyWords`.
  Without `class`/`instance` as keywords, `data Nat = Z | S Nat` followed

- Parser/Exp.hs:
    - `arrTy` is rewritten as a right-recursive parser and accepts
      `{{C}} -> t` anywhere in an arrow chain (e.g. `Int -> {{Eq a}} -> a`).
      Only `->` may follow `{{C}}`.
    - `simpleExpr` accepts `{{e}}` (`InstArg`); `simplePat` accepts `{{p}}`
      (`PInst`). Syntactically `{{e}}` may appear anywhere a simple

    - removed `classConstraint` and the stray `import GHC.RTS.Flags`.
- Surface.Syntax: pretty printing for the new constructs; the
  `where ... end` body of class/instance declarations is printed by
  `pprClassBody`.

Pretty-printing fixes (pre-existing issues)
-------------------------------------------

- Nullary type constructors were printed with parentheses and a trailing
  space (`Eq (Int )`): `pprPrec` for `TCon c []` now prints just `c`.
- Constructor arguments in `data` declarations lacked parentheses
  (`Cons a List a`): `NormalC` arguments are printed with `pprPrec 2`
  (the precedence of type-application arguments).
- Operator names lacked parentheses (`sig == : ...`, `def == ...`):
  added `isOpName` to the `QueryName` class (for each pass) and
  `pprVarName`, used for `sig`, `def` and `Var`. The operator characters
  in `isOpNameBase` must be kept consistent with `opRaw` in Parser/Id.hs.
  `fixity == 40` is printed without parentheses, as before.
- Type synonyms lacked `=` (`type Symbol  Char`): `DType` now prints
  `type T a1 ... an = ty`.
- Char literals were printed as `"'c'"` (Literal.hs): `ppr (show c)`
  showed the string `'c'` once more via `Pretty [Char]`; now `ppr c`.
- Removed extra spaces in `data T ` (no parameters) and `def x  = e`
  (no patterns).


Renaming (Renaming.hs)
======================

Decided and implemented item by item.

Expressions: `InstArg`
----------------------

- `{{e}}` is allowed only as an argument of an application:
  `App e1 (InstArg e2)` renames `e1` and `e2` as usual (free variables are
  those of `e1` and `e2`). An `InstArg` anywhere else is rejected:
    An instance argument {{...}} can only appear as an argument of a
    function application.
- Reason: `{{ }}` is not a value but a mark on how an argument is passed
  (it fills the next instance-argument binder of the applied function), so
  a standalone `{{e}}` has nothing to fill. The contents `e` themselves are
  an ordinary value (`def d = eqNat` is fine). Agda has the same rule:
  instance/hidden arguments are expressions in its concrete syntax but are
  rejected by the scope checker when not an argument of an application.
- Checking it in renaming lets later passes assume that `InstArg` occurs
  only as the argument of `App`.
- A parenthesized `({{e}})` is also rejected, since `Parens` sits between
  `App` and `InstArg` (e.g. `(\x -> x) ({{1}})`).

Patterns: `PInst`
-----------------

- `{{p}}` is renamed like a constructor argument; the bound variable is an
  ordinary local variable. `hasRev (PInst p) = hasRev p`.
- Restrictions (checked before renaming the patterns by `checkInstPatArg` /
  `checkNoInstPat`):
    (i)   The contents must be a variable or `_` (`{{x}}`, `{{_}}`).
          A class type has no constructors to match, and an instance
          argument is unrestricted, so `{{C x}}` and `{{rev x}}` make no
          sense.
    (ii)  `{{p}}` may appear only as an argument pattern itself of `def` or
          `\` (at any argument position, e.g. `def g n {{eq}} x = ...`).
          It is rejected in `case` alternatives, `let p <- e in ...`,
          `revdo` bindings, and inside other patterns (`C {{x}}`).
          Reason: `{{p}}`, dual to `{{e}}`, marks that the argument
          corresponds to an instance-argument arrow of the function type;
          other patterns match a single value and have no such arrow.
          Whether the position matches the type is checked by the type
          checker.
    (iii) All clauses of a `def` must have `{{ }}` at the same argument
          positions (in addition to having the same number of arguments).
          Clauses that omit instance patterns altogether are fine.
- Patterns have no parentheses node, so `({{x}})` is the same as `{{x}}`.
- Possible future relaxations (relaxing later keeps old programs valid):
    - constructors with instance arguments (GADT-style
      `sig C : {{Eq a}} -> a -> T`) would give meaning to `C {{x}} y`,
      as in Agda;
    - if a variable bound by `{{x}}` becomes an instance candidate in its
      scope (as in Agda), `let {{x}} <- e in ...` / `case e of {{x}} -> ...`
      could introduce local instances.

Class declarations: `DClass`
----------------------------

- (a) Method names are top-level names (as in Haskell): `(==)` declared in
  `class Eq a` becomes a top-level function of type
  `{{Eq a}} -> a -> a -> Bool`, referred to without qualification (as all
  samples do). Two classes, or a class and a top-level `def`, cannot have
  a method of the same name. (Rejected: Lean-style `Eq.(==)` with `open`,
  which needs qualified names inside a module and a new construct.)
- (b) Class parameters in method signatures (parser change, implemented).
  In existing Sparcl every `sig` is closed: the parser quantifies all free
  type variables of each `sig` by `introForAll`, and renaming renames a
  `sig` type in an empty type-variable environment (`renameTy 0 M.empty`),
  so a type variable of an outer `sig` cannot be referred to from a `sig`
  in its `where` clause (no scoped type variables; e.g. `sig g : a -> a`
  inside `def f` with `sig f : a -> a` gets its own `forall a`).
  Method signatures are the exception: their class parameters must refer
  to the class. Hence `classDecl` parses its body with
  `whereClauseWith (introForAllExcept xs)`, which does not quantify the
  class parameters `xs`:
    class C a where
      sig m : a -> b -> b         -- parsed as  forall b. a -> b -> b
      sig k : forall a. a -> a    -- explicit forall: shadows the class `a`
    end
  Renaming will rename method signatures with the class parameters in the
  environment, and the type checker will build the method type
  `forall a b. {{C a}} -> a -> b -> b` for `m` (all foralls in front; see
  type checking B-5). Whether a method type that does not
  mention a class parameter (as `k`) is allowed is left to type checking.
  (Rejected: stripping the outer `forall`s of the class parameters
  afterwards, which cannot tell them from explicitly written ones.)
  Added to Parser/Exp.hs: `introForAllExcept`, `localDeclWith`,
  `sigDeclWith`, `whereClauseWith` (the old names are the `introForAll`
  instances).
- (c) Checks on the class body:
    - `sig`: declares a method; duplicated method names in a class are
      rejected.
    - `def`: a default method; allowed only for a method declared by `sig`
      in the same class, at most one `def` per method (more clauses are
      written with `|`). Its name is resolved to the top-level method name
      and the right-hand side is renamed as usual. Its type comes from the
      method's `sig`.
    - `fixity`: allowed only inside the class body and only for methods of
      that class; it goes to the top-level operator table. A top-level
      `fixity` for a method is rejected, as before (top-level `fixity` is
      allowed only for names defined by top-level `def`).
      (Rejected: also allowing a top-level `fixity` for methods, as in
      Haskell.)
- (d) Superclasses `extends S1, ..., Sm`:
    - Each `Si` is renamed in the environment of the class parameters (as
      method signatures), so type variables other than the class
      parameters are rejected (`class Ord a extends Eq b` gives
      `Unbound type variable: b`); they are not quantified anywhere.
    - Renaming checks only the shape `TCon S ts`. Whether `S` is a class
      is checked by the type checker (it needs imported class
      information), as for instance types.
    - Left to later passes: names of superclass fields (such as Lean's
      `toEq`) are generated when dictionaries are built (type checking or
      desugaring), since users never write them and extracting `Eq a` from
      `{{Ord a}}` is done by instance search; cycles in the superclass
      hierarchy are detected by the type checker, where the information
      of all classes, including imported ones, is available.
      (Changed in type checking G-2, 2026-11-04: cycles are not detected
      but allowed; instance search stops by its depth limit, E-3 3.)

Instance declarations: `DInst`
------------------------------

- Named instances (`instance eqNat : Eq Nat ...`) are top-level value
  names, in the same name space as `def` (so `elem {{eqNat}}` works).
- (a) Unnamed instances get a name generated by renaming that users cannot
  write: a new `SystemName` constructor (e.g. `NInstance !Int`) numbered
  within the module, `Original currentModule (System (NInstance k)) ...`.
  Renaming always fills `DInst (Just x)`, so later passes can treat every
  instance as a named value; no clash with user names is possible.
  Pretty-printing is by the number at first (e.g. `<instance #3>`);
  printing the instance type would need the type in the name.
  (Rejected: Lean-style names from the type head such as `instEqList`,
  which may clash with user names or with each other; keeping `Nothing`
  until type checking, which makes every later pass handle `Maybe`.)
- (b) The instance type (already quantified by `introForAll` in the
  parser) is renamed by `renameTy 0 M.empty` and checked in renaming:
    1. Shape: `forall a1 ... ak. {{T1}} -> ... -> {{Tm}} -> C t1 ... tn`
       with each `Ti` of the form `TCon S ts`. Ordinary arrows
       (`Int -> Eq a`; instance search cannot supply explicit arguments),
       `forall` in the middle, and a head that is a type variable or an
       arrow are rejected. Whether `C` and `S` are classes is checked by
       the type checker.
    2. No restriction on the head arguments `t1 ... tn` (Haskell 98 would
       require `C (T a1 ... an)`; Agda and Lean have no such restriction).
       To be decided together with instance search (overlap, termination).
    3. Every type variable must occur in the head `C t1 ... tn`;
       e.g. `instance {{Eq b}} -> Eq Int` is rejected, since search for
       `Eq Int` cannot determine `b`.
    4. A named instance must not have the same name as a top-level `def`
       or a method. NB: there is no duplicate check among top-level names
       at all at present (`FIXME: check there is no overlaps in names.`
       in `renameTopDecls`).
- (c) The instance body:
    1. Only `def` is allowed. `sig` is rejected (the type is determined by
       the class `sig` and the instance type; cf. Haskell without
       `InstanceSigs`), and so is `fixity` (method fixities are written
       only in the class body).
    2. A `def` name is resolved to a top-level name by the usual name
       resolution. Whether it is a method of the instance's class is
       checked by the type checker (the name table does not distinguish
       methods from other names, and has no information on imported
       classes). Two `def`s of the same name in one body are rejected.
    3. Right-hand sides are renamed as usual; e.g. `l1 = l2` in the body
       of `Eq (List a)` refers to the global method, and the dictionary is
       chosen by instance search in the type checker.
    4. Missing methods without defaults are reported by the type checker.
  The instance arguments of the instance itself (`{{Eq a}}` of `eqList`)
  are found by instance search in the body but cannot be named, as in
  Haskell; a syntax for naming them is left for later.

Output of `renameTopDecls`
--------------------------

- (i) Classes and instances are returned as dedicated tuples, in the same
  way as `data` and `type` declarations (planned shapes):
    [Loc (Name, [Name], [LTy 'Renaming], [Loc (Name, LTy 'Renaming)], [LDecl 'Renaming])]
      -- class: name, parameters, superclasses, method signatures,
      --        default method definitions (DDef)
    [Loc (Name, LTy 'Renaming, [LDecl 'Renaming])]
      -- instance: name (generated if omitted), type, method definitions
  Method fixities go to the returned operator table.
  (Rejected: returning the `DClass` / `DInst` nodes themselves. That would
  reuse the AST and its pretty printer, but the type checker would have to
  rule out the other `TopDecl` constructors.)
  NB: only the `def`/`sig` part of the result is printed (`-v2`,
  `Module.hs`); the `data`/`type` tuples have no `Pretty` instance and are
  not printed, so neither will these be.
- (ii) Default methods and instance bodies are not mixed into the
  stratification (SCCs) of top-level `def`s; each body is a list of `DDef`s.
  The type checker is to (1) register all classes and instance types,
  (2) infer the top-level `def`s stratum by stratum, and (3) check default
  methods and instance bodies last. Their types are fully given by the
  declarations (like `def`s with `sig`s), so (2) never depends on (3), and
  (3) can use the inferred types of helper functions without `sig`.
  At run time this is fine: `desugarTopDecls` puts all top-level bindings in
  one `Bind`, which `evalUBind` evaluates as one recursive group (`rec`).
- (iii) `inferTopDecls` takes the class and instance lists as two more
  arguments and, until type checking of them is implemented, fails with
  "Type checking of class and instance declarations is not supported yet."
  if either is non-empty.

Implementation (Renaming.hs, all of the above)
----------------------------------------------

- `renameTopDecls` returns `[Loc ClassDeclR]` and `[Loc InstDeclR]`
  (type synonyms for the tuples above) in addition to the previous results.
- Top-level names now include class names, method names and instance
  names (including generated ones), so they are put in the name table and
  in the returned bound names.
- Duplicate check: each method and named instance is checked against the
  top-level `def`s, the methods and the named instances ("Duplicate
  definition of x"). Duplicates among other names are still not checked.
- Class fixities are collected before renaming anything (checking that
  they are for methods of the class) and are in effect for the whole
  module; they are also added to the returned operator table.
- Class and instance bodies are renamed after the top-level `def`s, under
  the top-level and class fixities. The clauses of a definition are renamed
  by `renameDefClauses`, factored out of `renameLocalDeclsWork` and shared
  by local, top-level, default method and instance method definitions.
- The instance type check is `checkInstTy`; superclasses and instance
  arguments of instances are checked by `isClassAppTy` (a `TCon` that is
  not an arrow).
- Name.hs: added `NInstance !Int` to `SystemName`, printed `<instance #k>`.
  Instances are numbered by their positions among the instance declarations
  of the module (named ones included).
- Error messages (checked with small files):
    Duplicate definition of m            -- method vs def, duplicated sig,
                                         -- duplicated instance name
    Default method k is not a method of class C
    Duplicate default method m in class C
    Fixity declaration in class C is allowed only for its methods: ++
    Fixity declaration is allowed only for the current level name: ++
                                         -- top-level fixity of a method
    Unbound type variable: b             -- class C a extends D b
    A superclass must be of the form C t1 ... tn: a
    The head of an instance must be of the form C t1 ... tn: Int -> C Int
    Type variable b does not occur in the instance head C Int
    An instance argument of an instance must be of the form C t1 ... tn: ...
    A signature declaration is not allowed in an instance declaration.
    A fixity declaration is not allowed in an instance declaration.
    Duplicate definition of method m in an instance declaration.
    Unbound name: zz                     -- instance method not defined anywhere
- All `Examples-Class/*.sparcl` (except `Functor.sparcl`, a parse error)
  pass renaming and stop at the type checker with the message above. The
  samples' method fixities were moved into the class bodies (`Eq.sparcl`,
  `Ord.sparcl`).


Type checking (Typing/*.hs)
===========================

Overall direction (by the author):
- Abstraction insertion: when checking an expression against a type that
  takes an instance argument, and the expression is not an abstraction
  taking an instance argument (`\{{d}} -> ...`), an abstraction is inserted.
- Application insertion: when checking an application whose head has a
  type taking an instance argument and the corresponding argument is not an
  instance argument `{{e}}`, an application to a new meta variable (an
  instance goal) is inserted.
- As in Lean and Agda, a chain of applications is first flattened into a
  head and a list of arguments (a spine) and then checked.

Positions of class types
------------------------

Decided (2026-11-03):
  - Q1 allowed: a class type is an ordinary type (the type of its
    dictionary) and may appear anywhere a type may (`Eq Int -> Bool`,
    `List (Eq a)`, `def d = eqNat`), as recorded in Design.
  - Q2 rejected: the type inside `{{ }}` must be an application of a class
    to the right number of arguments (`{{Int}}`, `{{a}}`, `{{Int -> Int}}`,
    `{{List a}}` are errors). Reason: instance search only considers
    declared instances (and instance-bound locals), so `{{Int}}` could only
    ever be filled explicitly, and for `{{a}}` the class to search is not
    even known. Checked by the type checker (it needs class information,
    including imported classes), on the types written by users after
    synonym expansion; see B-1 for the list of checks.

Two separate questions:
  (Q1) explicit use of class types: may a class type appear outside
       `{{ }}` (`sig h : Eq Int -> Bool`, `def d = eqNat`, `List (Eq a)`)?
  (Q2) implicit passing of non-classes: may a non-class type appear inside
       `{{ }}` (`sig f : {{Int}} -> Bool`, `{{a}}`, `{{Int -> Int}}`)?
What has been recorded / implemented so far:
  - Design (top of this note): "a class is an ordinary type constructor
    (the type of its dictionary)"; the ambiguity example there uses
    `sig f : {{Eq a}} -> Eq a -> a -> Bool`, i.e. Q1 = allowed was assumed.
    Renaming / InstArg: "The contents `e` themselves are an ordinary value
    (`def d = eqNat` is fine)". Type checking A-2 / A-3 also assume
    `Eq a -> ...` is a valid type.
  - History: a proposal to restrict class types to `{{ }}` positions
    (Haskell-like; with a dedicated `TInst` node) was discussed on
    2026-10-28 but that branch of the conversation was rolled back; the
    adopted proposal was "class = ordinary type, `TCon nameTyInstArr`,
    `InstArg`" (approved). No decision on Q2 is recorded.
  - Parser: `{{ typeExpr }} -> t` accepts any type inside the braces.
  - Renaming: no check of the contents of `{{ }}` in `sig` types; only
    instance types and superclasses are checked for the shape `TCon c ts`
    (`isClassAppTy`, which does not know whether `c` is a class, so
    `instance : List Int` passes renaming). Class types outside `{{ }}` are
    not checked either. Verified: `sig f : {{Int}} -> Bool` and
    `sig g : {{a}} -> {{Int -> Int}} -> Bool` pass parsing and renaming
    (then hit the unimplemented `PInst` case of the type checker);
    `sig h : Eq Int -> Bool` passes renaming.
  - Samples (Examples-Class/): class types occur only inside `{{ }}`, in
    instance heads and in `extends`; instance names are used only inside
    `{{ }}`. Neither Q1 nor Q2 is exercised. No test (Nonexamples) covers
    them.

Scope and staging (kinds)
-------------------------

Higher-kinded classes (`class Functor f`, `f : Type -> Type`) are in the
scope of this extension, but are handled in a separate, later stage
("kinds and higher-kinded types"); plan (alpha).
- Current Sparcl has no kind checking (`typeKi` / `arrKi` in Type.hs are
  unused) and no arity check of type constructors (`ty2ty` maps
  `TCon c ts` to `TyCon c ts` as is; e.g. `List Int Int` is probably
  accepted). Multiplicity variables (`p` in `a # p -> b`, `q <= s`) are
  ordinary type variables, distinguished only by position.
- First stage (now): type checking of classes/instances for first-order
  classes (all class parameters of kind `Type`); Eq/Ord-like examples.
  Instead of kind checking, ad hoc checks using the class table (B-1;
  see "Positions of class types"): the type in `{{ }}`, an instance head
  and a superclass are applications of a class, and every application of
  a class (inside or outside `{{ }}`) has the right number of arguments
  (rejects `{{List a}} -> ...`, `{{Int}}`, `instance : List Int`,
  `{{Eq a b}}`, `Eq a b -> Bool`; `Eq a -> Bool` is accepted). These
  checks are to be subsumed by kind inference later, except "is a class"
  (inside `{{ }}`, instance heads, superclasses), which stays a check via
  the class table since classes have kind `... -> Type` (I1).
- Later stage: kind inference (kinds `Type`, `Multiplicity`, `k -> k`,
  kind meta variables; a class has kind `k1 -> ... -> kn -> Type`, like a
  data type, since a class type is an ordinary type (Q1) and there is no
  separate `Constraint` kind (I1); class/data/type parameters and sig type
  variables are inferred, since e.g. the kind of `f` in Functor is written
  nowhere), with
    1. parser / surface AST: type-variable application `f a`
       (e.g. `TApp`);
    2. internal `Ty`: application headed by a variable / meta variable
       (e.g. `TyApp Ty Ty`);
    3. `unify`: partially applied `TyCon` (`TyApp f a` ~ `TyCon List [Int]`
       gives `f := TyCon List []`);
    4. a kind table in `ModuleContext`, kinds of built-in types in
       `baseModuleInfo`;
    5. instance heads such as `Functor List` (`TyCon Functor [TyCon List []]`)
       in instance search.
  The design of B-H hardly depends on this; expected rework: kinds of
  class parameters in `ClassInfo`, partial applications in matching.
- Why (alpha) rather than building kinds first (beta): smaller steps, each
  checked with existing tests and class examples; changes to `Ty` / `unify`
  are separated from the class machinery, which eases isolating
  regressions. Cost: the ad hoc checks above are temporary.

Internal representation of types
---------------------------------

- (A-1) A pattern synonym `InstFunTy c t` for `TyCon nameTyInstArr [c, t]`
  is added to Typing/Type.hs, like `FunTy`, and `Pretty Ty` prints it as
  `{{c}} -> t` (same precedence as `->`). No new `Ty` constructor, as in
  the surface AST: functions traversing `Ty` (`substTy`, `zonkType`,
  `capLevel`, `metaTyVarsGen`, `freeTyVars`, ...) and `unify` work
  unchanged. NB: since the generic `TyCon` treatment silently applies to
  `InstFunTy`, places that must treat it differently (subsumption, matching
  argument patterns against arrows, application) need explicit cases; the
  compiler does not warn about missing ones.
- (A-2) No change to `ty2ty` (`S.TCon` is mapped to `TyCon`, so `{{C}} -> t`
  becomes `InstFunTy C t`), `unify` (same-named `TyCon`s are unified
  componentwise after an arity check), substitution / zonking,
  `resolveSyn` (synonyms such as `type EqF a = {{Eq a}} -> a -> Bool` are
  expanded as usual), generalization and `quantify`. Notes:
    - `unifyWork` reports `UnMatchTy` for different constructor names, so
      `{{Eq a}} -> Bool` and `Eq a -> Bool` do not unify, as intended
      (instance arguments and ordinary arguments are different).
    - A meta variable may be bound to an `InstFunTy` (e.g. an argument of
      `sig k : ({{Eq a}} -> a -> Bool) -> ...`); this is a valid type and
      is not prohibited. Its interaction with "no application insertion for
      a head whose type is a meta variable" is discussed in D-5.
    - `numberOfArgs` in Desugar.hs counts only `nameTyArr` arrows to decide
      the number of arguments of a definition; it must also count
      `InstFunTy` (see H-4, desugaring). [Corrected by H-4-1: it is used
      only for eta-expanding constructors (`Con` / `RCon`); the arity of a
      `def` comes from its patterns (`desugarRHS`). It counts `InstFunTy`
      too, in preparation for constructors with instance arguments; no
      effect now (D-4).]
- (A-3) `subsumptionCheckBody` gets a case
    (InstFunTy c1 r1, InstFunTy c2 r2) ->
      tryUnify c1 c2; subsumptionCheckBody isRightGiven r1 r2
  The class types are compared by equality (they are monotypes, so
  contravariance is meaningless) and the results covariantly (as for
  `FunTy`). Without it, two `InstFunTy`s would fall into the final
  `unify` case and their results would be compared by equality.
  `InstFunTy` vs `FunTy` stays a type error (via `ensureFunTy`).
  Subsumption never elaborates terms, so no instance argument is inserted
  here (e.g. `forall a. {{Eq a}} -> a -> Bool` is not usable as
  `Nat -> Bool` by subsumption); insertion happens only in C (abstraction)
  and D (application), based on the shape of expressions.
  Why `InstFunTy` vs `FunTy` is an error although it would be sound (both
  are functions taking a dictionary at run time, so either direction
  could be accepted without changing terms):
    1. consistency with `unify`, which distinguishes them: subsumption is
       used only at the outer arrows, unification under type constructors,
       so identifying them only in subsumption would make
       `k elemD` (k : (Eq a -> a -> Bool) -> ...) accepted but
       `ks (Cons elemD Nil)` (ks : List (Eq a -> a -> Bool) -> ...) rejected;
    2. keeping "whether an argument is inserted is fixed by `{{ }}` in the
       type" (D, C-2) predictable;
    3. Agda (as far as we recall) does not identify Pi types of different
       visibility, while Lean 4 ignores binder info in definitional
       equality; there are precedents either way;
    4. conversions are easy to write by eta-expansion:
       `\{{d}} -> h d`, `\d -> f {{d}}`.
  (Alternative: identify them, as in Lean; then `unify` must do so too.)
- (A-4) `ensureFunTy` is unchanged: it is for ordinary arrows only (an
  `InstFunTy` given to it is a type error by unification, as in A-3), and
  no `ensureInstFunTy` is introduced, i.e., the type checker never
  instantiates a meta variable to an `InstFunTy` on its own. A type is an
  `InstFunTy` only when it comes from a signature (a meta variable may
  still become one by unification with such a type, A-2).
  `ensureInstFunTy` would be needed only where an explicit `{{ }}` meets a
  type that is still a meta variable:
    1. an instance pattern `{{p}}` without a known expected type (`def`
       without `sig`, `\{{d}} -> ...` in Infer mode) -> an error requiring
       an annotation (C-4);
    2. an explicit instance argument `f {{e}}` where the type of `f` is a
       meta variable -> an error (D-1, D-5).
  Why: (i) instance arguments are not inferred (otherwise `{{C a}} ->`
  would appear in, and be generalized into, types of unannotated
  definitions), and (ii) insertion (C-1, D-1) depends on whether a type is
  an `InstFunTy` when it is checked, so a checker-made path turning a meta
  variable into an `InstFunTy` would make insertion decisions more
  dependent on the checking order (the remaining path via unification is
  discussed in D-5).
  Uses of `ensureFunTy` in `App`/`Op` are replaced by the spine checking
  (D-1, D-3), which uses it only for `FunTy` and for explicit arguments
  applied to a meta variable; `ensureFunTyN` is replaced by the
  instance-aware alignment (C-2).

Class and instance environments
-------------------------------

- (B-1) A class table in TCMonad.hs:
    data ClassInfo = ClassInfo
      { ciParams   :: [TyVar]       -- class parameters (BoundTv of Alpha 0..)
      , ciSupers   :: [Ty]          -- superclasses (ciParams free)
      , ciMethods  :: [(Name, Ty)]  -- methods and their sig types (ciParams free)
      , ciDefaults :: [Name]        -- methods with a default implementation
      }
    type ClassTable = Map Name ClassInfo
  built from `ClassDeclR` by `ty2ty`; class parameters stay `BoundTv` and
  are instantiated by `substTy` when used. `TypingContext` gets
  `tcClassEnv :: !ClassTable`, a read-only environment like `tcSyn`
  (set via `runTCWith` / `setEnvs`, together with B-4). Used for method
  types (B-5), checking instance declarations (G: missing/extra methods,
  defaults, superclasses), superclass projections in instance search
  (E-3), and the ad hoc class checks replacing kind checking (see "Scope
  and staging" and "Positions of class types"). Class types such as
  `Eq a` are plain `TyCon Eq [a]` and are valid anywhere (Q1);
  classes are not registered as type constructors (there is no kind
  table yet). In the later kinds stage, `ClassInfo` gets the kinds of
  its parameters and class names get kinds `... -> Type` (I1).
- (B-2) Instance table and instances in the value environment.
    1. The type of an instance is its declared type (`InstDeclR`) made a
       polytype by `ty2ty`, e.g. `eqList : forall a. {{Eq a}} -> Eq (List a)`.
       By Q1 an instance is an ordinary value of a class type.
    2. `type InstTable = Map Name (Map Name Ty)` (class name -> instance
       name -> type; amended by B-4 (5) from `Map Name [(Name, Ty)]` so that
       the same instance reached by several import paths is one entry);
       `TypingContext` gets `tcInstEnv :: !InstTable`
       (read-only, as B-1). The global candidates of instance search are
       exactly the entries of this table, i.e. instance declarations; an
       ordinary `def myEq : Eq Nat = ...` is not a candidate (I3, global
       side; the local side is B-3).
    3. Instance names (including generated `System (NInstance k)` ones,
       which users cannot refer to) are registered in `tcTyEnv` with these
       types as ordinary global values, so `elem {{eqNat}} x xs` and
       `def d = eqNat` are typed by the existing `Var` case. Global values
       are unrestricted, so no multiplicity treatment is needed.
    4. Both are registered before any `def` is checked (G: "register
       first"), since the types depend only on the declarations; hence
       instances can be referred to from `def`s and from each other
       regardless of the declaration order.
    5. Checked at registration (G-1): the head is an application of a
       class with the right number of arguments (`isClassAppTy` in
       renaming checks only the shape, so `instance : List Int` is
       rejected here), and the instance arguments satisfy Q2.
- (B-3) Scope of local instances.
    1. `TypingContext` gets `tcLocalInsts :: ![(Name, Ty)]` (variable and
       its class type, which may contain skolems of the enclosing sig),
       extended by `local` (`withLocalInst`), like `tcTyEnv`.
    2. Registered (I3, local side): (a) variables bound by `{{x}}` (C-3),
       including `{{_}}` (renaming names it `Alpha level (User "_")`;
       `{{_}}` means "unnamed", not "not an instance"); (b) variables of
       inserted abstractions (C-1). Instance arguments in instance bodies
       and the class's own `{{C a}}` in default methods (G) come in as (a)
       or (b), since those bodies are checked against `InstFunTy`.
    3. Not registered: variables of a class type bound otherwise (ordinary
       patterns, `let`, `def`, `case`; e.g. `\d -> ...` with `d : Eq a`,
       allowed by Q1). As in Agda, only what is bound as an instance is a
       candidate, so candidacy is decided by the syntactic mark `{{ }}`.
    4. Variables of (a) are also put in `tcTyEnv` (by `withVar`, Omega), so
       by Q1 `eq` from `{{eq}}` is an ordinary value (`elem {{eq}}`,
       `let d = eq`).
    5. Lexical scope, as the value environment: visible in inner
       expressions, `where` clauses and local `def`s. Example:
         sig count : {{Eq a}} -> a -> List a -> Int
         def count {{eq}} x xs = go xs
           where
             def go Nil         = 0
                  | (Cons y ys) = case y == x of
                                    True  -> 1 + go ys
                                  | False -> go ys
                                  end
           end
       `a` is a skolem of `count`, `eq : Eq a` is a local instance,
       `x : a`. In `go` (no sig), `y == x` instantiates
       `(==) : forall b. {{Eq b}} -> b -> b -> Bool` with `?b`, inserts a
       goal `Eq ?b` (keeping the visible locals `[eq]`), and `y`, `x` give
       `?b = a`. After `go`'s body the goal is `Eq a`; no global instance
       head matches the skolem `a`, so it is solved uniquely by `eq`;
       `go : List a -> Int` (not generalized over the outer skolem).
       Without `{{eq}}` (`def count x xs = ...`), the variable of the
       inserted abstraction (C-1) plays the same role.
       A goal keeps the list at its creation (E-1), so it is searched in
       the right scope even when solved later. Local variables are named
       by de Bruijn levels (`Alpha`), unique along a scope path, so inner
       bindings cannot capture a candidate.
    6. Variables of inserted abstractions get names
       `Generated i TypeChecking` (a new `Phase` constructor), numbered by
       a new counter in `TypingContext`. `Generated` is used only by
       Desugar (numbered from 0) and REPL now; separate phases avoid
       clashes.
- (B-4) Classes and instances across modules (Module.hs).
  Existing module system (for reference): `module M (x, y) where` (optional;
  default `Main` without an export list), `import M` / `import M (x, T)`
  (bare names only; no `T(..)`, constructors are listed separately);
  modules are found as `M.sparcl` (`A.B` -> `A/B.sparcl`) in the search
  path, processed once and cached by module name; `Base` is implicit.
  Without an export list a module exports exactly its own definitions (no
  re-export); with one, the listed names among its own and imported ones.
  Import/export lists filter all tables by names (`restrictNames`).
  No sample or test uses modules.
    1. `ModuleContext` gets `mcClassTable :: ClassTable` and
       `mcInstTable :: InstTable`; `inferTopDecls` also returns the module's
       class and instance tables, and its `nts` include the types of
       instances and methods; `execTCWith` / `runTCWith` take both tables
       and set `TypingContext` (B-1, B-2).
    2. Class and instance tables are not filtered by import/export lists
       (`restrictNames` leaves them), as in Haskell / Lean: instances are in
       effect whenever their module is loaded. Unnamed instances cannot be
       listed; class information is needed for search (superclasses)
       whenever a class occurs in an imported type, even if its name is not
       imported. Visibility of names (`eqNat`) is still controlled by the
       name table.
    3. Transitive: the tables of a new module are its own plus those of all
       imported modules, with or without an export list (types of B's
       functions may mention A's classes, needed when C imports only B).
    4. Run time: a `Var eqNat` inserted by search needs the value even if
       the name is not imported, so `restrictNames` does not filter value
       table entries of names in the instance table (unnamed ones
       included). Default methods and superclass projections may need the
       same; to be checked with the dictionary representation (H-4).
       [Settled by H-4-5: `NSuperProj` / `NDefault` names are kept too, and
       these values are propagated transitively.]
    5. `InstTable` is `Map Name (Map Name Ty)`, merged by
       `M.unionWith M.union` (diamond imports deliver the same instance
       twice; plain list concatenation would make search ambiguous). Class
       tables are merged by `M.union`.
  Uniqueness of instance names: `Name` equality of `Original` compares
  (module name, base name); names are unique within a module (renaming's
  duplicate check; `NInstance k` by position, a `System` name), and module
  names are unique in a loaded program (cache by name, check that a file
  defines the imported module name). So "same name, different instance"
  cannot occur (except the `Main` issue in TODO); different instances for
  the same class and type in different modules (`A.eqNat`, `B.myEqNat` :
  `Eq Nat`) are not merged and are an overlap issue for E-4 (detect at
  merge or at use).
  How Agda / Lean treat several distinct matching candidates (Agda part
  checked in its documentation, 2026-11-04; Lean from memory): Agda
  unifies each candidate's type with the goal and discards only definite
  mismatches (metas of the goal may be instantiated); none -> error,
  exactly one (non-incoherent) -> chosen, several -> postponed, error if
  still ambiguous at the end; local instance variables are candidates
  with no stated priority over global ones (overlap pragmas /
  `--overlapping-instances` in recent versions). Lean 4
  does not report ambiguity: candidates are tried by priority, then the
  most recent first, with backtracking; overlap is allowed (incoherence
  possible). Haskell rejects overlap at use sites unless pragmas.
- (B-5) Global types of methods: all foralls in front, plan (b).
  For `class C a1 ... an` and a method `sig m : forall bs. cs => t`
  (the parser quantifies only the non-class variables `bs`; `cs` are
  multiplicity constraints), the global type of `m` is
    forall a1 ... an bs. cs => {{C a1 ... an}} -> t
  e.g. `sig m : a -> b -> b` in `class C a` gives
  `forall a b. {{C a}} -> a -> b -> b`.
  Since `bs` do not occur in `C a1 ... an`, this is equivalent to the
  nested form `forall as. {{C as}} -> forall bs. cs => t` (plan (a)),
  which Haskell / Lean / Agda use; there the order is observable through
  explicit type application or named implicit arguments, which Sparcl
  does not have.
  Why (b): `Var` is instantiated at once by the existing `instantiatePoly`
  (with (a) the `forall bs` left after the inserted instance argument
  must be instantiated again); multiplicity constraints stay at the top as
  in ordinary `sig`s instead of a `TyQual` under an arrow (higher-rank
  path); methods do not depend on D-1 instantiating a `TyForAll` in the
  middle of a spine (which D-1 still supports for user-written
  `{{Eq a}} -> forall b. ...`). Checking instance bodies (G) uses the sig
  types in `ciMethods`, so it does not depend on this choice.
  No capture: sig type variables are named by `Alpha` indices distinct
  from the class parameters, also when an explicit `forall a` shadows a
  class parameter. Renaming (b) is fixed accordingly (I2).

Abstraction insertion
---------------------

- (C-1) At the entry of `checkTy` (before `go expr`): if the expected type
  is `Check t` and `t` zonks to `InstFunTy c t'` (zonk: a meta variable
  may hold an `InstFunTy`, A-2), a fresh `d = Generated i TypeChecking`
  (B-3 (6)) is registered with type `c` in the value environment (Omega)
  and as a local instance (B-3), and the same expression is checked
  against `t'` (recursively, so `{{Eq a}} -> {{Ord b}} -> ...` gives two
  abstractions). Result: `Abs [PInst (PVar (d, c))] e'`; `d` is removed
  from the use map (Omega, so no multiplicity constraint). Being at the
  entry, it applies to every form of expression.
  No insertion:
    - Infer mode (no expected type; A-4, C-4);
    - expected type still a meta variable (A-4, D-5);
    - `Abs` whose first pattern is `{{p}}`: bound by the user; C-2 aligns
      it with the `InstFunTy`;
    - `Parens`: the expected type is passed inside and decided there
      (otherwise `(\{{d}} -> e)` would get an insertion outside and its
      `{{d}}` would face a `FunTy`);
    - `Sig` `(e : T)`: `e` is checked against `T` (inserting there if `T`
      is an `InstFunTy`), then `T` is compared with the expected type by
      subsumption (A-3); inserting first would compare `T` with `t'` and
      always fail when `T` is `{{...}} -> ...`.
  Example: `sig g : {{Eq a}} -> a -> a -> Bool; def g = (==)`: the body
  `(==)` is checked against `{{Eq a}} -> a -> a -> Bool` (`a` skolem);
  `d : Eq a` is inserted and `(==)` is checked against `a -> a -> Bool`;
  `(==)`'s leading `{{Eq ?b}}` gets a goal by D-2, `?b = a`, solved by `d`;
  the result is `\{{d}} -> (==) {{d}}`.
  Polytypes need nothing special: `checkPolyTy` skolemizes, and the body
  type starting with `InstFunTy` is handled at the entry of `checkTy`.

  compare the expected type with the synthesized type before subsumption

  `(\p -> e2) e1`); if the synthesized type is also an `InstFunTy`, unify

    1. Non-spine forms (`Abs` in Check mode, `Let decls`, `Case`, `RDO`,

    3. (Q) would accept `sig k : forall b. {{C b}} -> Int`,

- (C-2) `ensureFunTyN` (`inferMutual` with and without sig, `Abs` in Check
  mode) is replaced by `alignPatsTy :: [LPat] -> BodyTy -> TC ([Slot], BodyTy)`
  with `Slot = Explicit (PolyTy, MultTy) | Inst c | Inserted c`. It zonks
  the type and aligns patterns with arrows from the left; each row
  consumes at most one pattern and is repeated on the rest of the type:
    type            next pattern            action
    InstFunTy c t   {{p}}                   Inst c, consume the pattern
    InstFunTy c t   other (patterns left)   Inserted c, consume nothing
    FunTy           {{p}}                   error ("not an instance argument")
    FunTy           other                   Explicit (as now)
    meta            {{p}}                   error: "an instance pattern needs
                                            a type annotation" (C-4 (b))
    meta            other                   Explicit by ensureFunTy (as now)
    anything        no patterns left        stop; the rest is the body type
  (A run of metas without `{{p}}` is exactly `ensureFunTyN`, which is
  `ensureFunTy` repeated.) With a meta and a later `{{p}}`, `ensureFunTy`
  first binds the meta to a `FunTy` and the `{{p}}` then hits the
  "meta / {{p}}" row; the accepted programs are the same as with a
  look-ahead check (the rest is a fresh meta, not unified elsewhere before
  the patterns are checked), so the simpler per-step rule is used, with
  the error reported at the `{{p}}`. Metas occur in the spine only without
  a sig (sigs are closed and skolemized) or for `\ ... {{p}} ...` whose
  type is unknown (e.g. an argument of `id`).
  Use in clauses and `Abs`: an `Inst c` slot checks the pattern with
  multiplicity Omega against `Check c` (C-3); an `Inserted c` slot puts a
  new `PInst (PVar d)` at that position and registers `d` (B-3). So after
  type checking, the patterns of every clause correspond one-to-one to
  the arrows (`FunTy` / `InstFunTy`) of the type, which desugaring can
  rely on (H-4: `numberOfArgs` counts `InstFunTy` [corrected by H-4-1:
  the arity of a `def` comes from its patterns; `numberOfArgs` is for
  constructors]). By Renaming (iii) all
  clauses have `{{ }}` at the same positions, so the alignment is computed
  once from the first clause (as `numPatterns` now) and applied to all;
  inserted variables are fresh per clause. [Revised at stage 5, approved
  by the user 2026-11-07: the variable of an inserted pattern is
  generated once per definition by `alignPatsTy` (`Inserted d c`) and
  shared by all its clauses. Reason: desugaring (`desugarAlts`) groups
  clauses whose non-invertible patterns are equal into one invertible
  case (`RCase`); variables written by the user at the same position are
  equal (renamed to `Alpha` names, compared by position), but fresh
  inserted variables were not, so e.g. `Invertible.sparcl`'s
  `rsucc (rev Nil) = ... | (rev Cons x xs) = ...` for `List a` became two
  cases, the first always taken, and `fwd rsucc (Cons ...)` failed with a
  pattern-match failure. Each clause binds the shared name in its own
  scope, so sharing is safe. Alternative not taken: make `desugarAlts`
  ignore variable names and rename per clause (more general, but needs
  renaming in the typed body).]
  Trailing `InstFunTy` after the patterns are exhausted is left to C-1 in
  the body (plan (1)). Rejected: absorbing it in the clause, which would

    def f x = \{{d}} -> x == x          -- body checked against Bool

Application insertion
---------------------

- (D-1) Applications are checked as spines (replacing `go (App e1 e2)`,
  `Typing.hs:481`, which infers `e1`, applies `ensureFunTy`, checks `e2` by
  `checkPolyTyM` and compares the result with `instantiatePoly`).
    1. A chain `e0 a1 ... an` is split into the head `e0` and arguments
       `Explicit e` / `Inst e` (`InstArg`); `Parens` around the head is
       crossed (D-6).
    2. Head type: for `Var x`, the polytype from `askType` as is (not
       instantiated); otherwise `inferTy` (may be an `InstFunTy`, e.g.
       `(g : {{Eq Int}} -> Int -> Bool) 3`).
    3. Arguments are processed from the left, zonking the current type at
       each step:
         type            next argument   action
         TyForAll        (any, or none)  instantiate with fresh metas;
                                         multiplicity constraints become
                                         wanted, as `instantiate` does now
         InstFunTy c t   Inst e          check `e` against `Check c`; uses
                                         raised by Omega
         InstFunTy c t   Explicit e      insert an application: create a goal
                                         (E-1) and put `InstArg (InstHole ref)`
                                         (F-3);
                                         the argument is not consumed
         FunTy m a r     Explicit e      `checkPolyTyM e a m` (as now)
         FunTy           Inst e          error "not an instance argument
                                         position"
         meta            Explicit e      `ensureFunTy`, then the FunTy row
                                         (as now)
         meta            Inst e          error "an instance argument cannot be
                                         passed to a function of unknown
                                         type" (A-4)
         other           Explicit e      `ensureFunTy` fails by unification
                                         (as now)
    4. After the arguments: leading `forall` / `InstFunTy` of the rest are
       handled by D-2; then the rest is compared with the expected type by
       `instantiatePoly`, as now.
    5. Use maps: the head's and each argument's, the latter raised by the
       multiplicity of its arrow; `Inst` and inserted arguments by Omega.
    6. Result AST: nested `App`s rebuilt, including inserted `InstArg`s;
       the head `Var` carries its polytype (`Var (x, tyOfX)`), as now.
    7. A `Var` without arguments also goes through this (a spine with zero
       arguments), since trailing insertion (D-2, `def g = elem`) applies to
       it. Without arguments and without `InstFunTy` in the rest, the
       result is the same as the present `instantiatePoly tyOfX expectedTy`,
       so higher-rank checking (`Examples/Poly.sparcl`) is unchanged.

Instance search
---------------

- (E-1) Postponed goals. An application inserted by D-1 / D-2 usually has
  metas in its goal (`Eq ?a` in `elem x xs` is fixed by the later `x`), so
  goals are recorded and solved later.
    1. TCMonad.hs:
         data Goal = Goal
           { goalId     :: Name             -- for messages / debug output
           , goalRef    :: IORef (Maybe (LExp 'TypeCheck))
                                            -- the hole in the AST (F-3)
           , goalTy     :: Ty               -- class type, may contain metas
           , goalLocals :: [(Name, Ty)]     -- tcLocalInsts at creation (B-3)
           , goalLevel  :: TcLevel          -- tcTcLevel at creation (E-2)
           , goalCtx    :: TypeErrorContext -- for error messages
           }
       `goalLocals` keeps the scope of creation, so a goal solved later is
       searched in the right scope (B-3 (5)).
    2. `TypingContext` gets `tcGoals :: !(IORef [Goal])`, appended on each
       insertion and emptied by `refreshTC` like the other IORefs.
    3. `gatherGoals :: TC a -> TC (a, [Goal])`, shaped like
       `gatherConstraint` (save, collect the new goals, restore), delimits
       the goals of a definition (where they are solved, E-2) and is used to
       put unsolved ones back into the outer list.
    4. (Amended by F-3 (b), 2026-11-04.) A solved goal's dictionary
       expression (e.g. `eqList {{eqNat}}`) is written to its `goalRef`;
       the earlier `tcGoalSols :: IORef (Map Name (LExp 'TypeCheck))` in
       `TypingContext` is dropped.
    5. Not mixed with `tcConstraint` (`InferredConstraint`s: multiplicity
       and type equalities, solved by the SAT solver); instance goals are
       solved quite differently (matching candidates, recursive search).
- (E-2) When goals are solved, and generalization.
  Found: Sparcl does not generalize local `def`s without sig
  (`tryGeneralizeTy`, `Typing.hs:695`: zonk only unless top level); only
  top-level sig-less `def`s are generalized.
  Goals are solved in `inferMutual` after the bodies of a group are
  checked, before generalization (the next top-level group uses the
  generalized type) and before solving multiplicity constraints
  (instantiating a candidate may add constraints): the group's goals are
  collected by `gatherGoals`, zonked and searched (E-3, E-4). Unsolved:
    no metas and no candidate                -> error "no instance"
    local group (not generalized), metas     -> put back into the outer
                                                list (outer uses may fix
                                                the metas)
    top-level sig-less def, metas that would -> error, plan (a): instance
      be generalized                            arguments are not inferred;
                                                write a sig
    top-level def with sig, metas left       -> error "ambiguous" (nothing
                                                outside can fix them)
    anything left after a top-level group    -> error
  E.g. `let def same y z = y == z in same 1 2`: `Eq ?b` from `same` is
  postponed outward and solved after `same 1 2` gives `?b = Int`; no sig
  needed.
  Rejected for top-level sig-less defs: (b) adding `{{Eq a}} ->` and
  generalizing (Haskell's constraint inference; infers instance arguments,
  against A-4 / C-4 / D-2); (c) not generalizing those variables (like
  Haskell's monomorphism restriction): at top level there is no outside,
  so the first use in a later group would fix the type, depending on
  definition order, and still an error if never fixed. Lean / Agda do not
  add implicit arguments to top-level definitions by inference (from
  memory, not checked).
  Consequences: all sig-less defs of the samples solve their goals in
  place (checked at C-4); `def g = elem` needs a sig (D-2).
- (E-3) Search for a zonked goal `C ts` with the goal's local instances
  (E-1) and the instance table (B-2).
    1. Candidates:
       (i)   local instances `d : C ss` (dictionary `Var d`);
       (ii)  superclasses of local instances: `d : Ord t` gives `Eq t`,
             transitively and for every class in `extends` (on demand,
             within the depth limit of 3; amended by G-2); dictionary
             `proj_{Ord,0} d`, where projections are global functions with
             `System` names (users cannot write them), one per class and
             superclass index, whose values are made by desugaring (H-4);
             this realizes Renaming (d)'s "superclass field names are
             generated later";
       (iii) global instances of class `C` in the instance table, of type
             `forall as. {{H1}} -> ... -> {{Hk}} -> C us`.
    2. A global candidate is instantiated with fresh metas and its head
       `C us` matched with `C ts` (matching rule: E-4); on success
       `H1 ... Hk` are solved recursively as goals under the same local
       instances. Dictionary: `inst {{e1}} ... {{ek}}`, i.e.
       `App (Var inst) (InstArg e1) ...` in the typed AST, the same shape as
       insertions by D-1.
    3. A depth limit (e.g. 32) on the recursion; exceeding it is an error
       "instance search too deep (possibly cyclic instances)", e.g. with
       `instance {{Eq (List a)}} -> Eq a`.
       (Amended by G-2, 2026-11-04.) The limit counts both the recursion
       on subgoals of global candidates and each projection step of (ii),
       with one shared bound, so search also stops with cyclic
       superclasses (`class A a extends B a`, `class B a extends A a`,
       which give `B a`, `A a`, `B a`, ... from `{{A a}}`) and with
       growing ones (`class A a extends A (List a)`, where a visited set
       would not help).
    4. Superclasses of global instances are not followed (as Haskell): a
       goal `Eq Int` is not solved by projecting the global `Ord Int`. G
       checks, when registering a global instance, that its superclass
       instances are solvable, so `Eq Int` is found directly; following
       projections too would give a second candidate and spurious
       ambiguity. (Lean registers `extends` projections as instances and
       follows them; from memory, not checked.)
    5. Several matching candidates are E-4: local and global (`{{Eq Int}}`
       of D-2), locals overlapping (`{{Ord a}} -> {{Eq a}} -> ...` gives
       `Eq a` directly and by projection), and globals overlapping.
- (E-4) Matching and several candidates (all as recommended).
    (1) One-way matching: only the candidate's type variables may be
        instantiated, never the goal's metas; a goal that cannot be decided
        because of metas is "stuck" (postponed). `Eq (List ?a)` matches
        `eqList`'s head `Eq (List a)` with `a := ?a`, so it is committed and
        the subgoal `Eq ?a` postponed; `Eq ?a` unifies with almost every
        global head but matches none one-way, so it is postponed. Stuck
        goals at the solving point follow E-2's table (postponed outward or
        "ambiguous"). Why: metas fixed by search cannot be undone if later
        checking disagrees; Haskell also waits for the goal to be
        instantiated before choosing.
    (2) Local over global: if any local candidate (projections included)
        matches, globals are not considered
        (`sig f : {{Eq Int}} -> Int -> Bool; def f x = x == x` uses the
        argument). As Haskell's givens and Lean's local instances.
    (3) Several locals: not an error; a fixed order picks one: direct local
        instances before projections; within a kind, the innermost (most
        recently bound) first (as Lean). E.g.
        `sig h : {{Ord a}} -> {{Eq a}} -> ...` uses the direct `Eq a`.
        Rejecting it would reject ordinary code. NB: since `{{e}}` can pass
        different dictionaries explicitly, the candidates need not agree
        (incoherence); the choice is by this fixed rule.
    (4) Global overlap, two stages:
          - at declaration (G-1): a head of an instance declared in the
            module that unifies (after renaming type variables apart) with
            the head of any visible instance (own or imported) is an error;
          - at use: overlaps from different modules (B-4: `A.eqNat`,
            `B.myEqNat`) cannot be seen at declaration; two matching global
            candidates at a use site are an ambiguity error (as Haskell).
            Not detected when tables are merged, which would reject merely
            importing both.
        REVISED 2026-11-04 (G-3, plan (A), as Agda): no check at
        declaration; overlapping instances may be declared, and overlap is
        handled only by search. Since the declaration check was what made
        committing by one-way matching safe in (1) (with `Eq (List a)`
        and `Eq (List Int)` both declared, committing `Eq (List ?a)` to the
        former would be wrong once `?a := Int`), the decision rule of (1)
        becomes (metas of the goal are still never instantiated):
          L. Locals (with projections): if some match one-way, pick one by
             (3). Else, if some unify with the goal, the goal is stuck
             (one may match once metas are fixed). Else go to G.
          G. Globals: U = the candidates whose head unifies with the goal
             (type variables renamed apart; only definite mismatches are
             excluded, as Agda; skolems are rigid).
               |U| = 0                      -> `NoInstance`
               |U| = 1, matches one-way     -> commit; subgoals (E-3 2)
               |U| = 1, does not match      -> stuck (needs goal metas)
               |U| >= 2, goal has metas     -> stuck
               |U| >= 2, goal has no metas  -> `AmbiguousInstances`
          Stuck goals follow E-2's table (postponed outward; at top level
          `AmbiguousGoal`). E.g. with only `eqList`, `Eq (List ?a)` is
          committed as before; with `Eq (List Int)` also declared it is
          stuck until `?a` is known; `Eq (List a)` with a skolem `a` is
          committed to `eqList` (`Int` vs skolem is a definite mismatch);
          `Eq (List Int)` is `AmbiguousInstances`.
        Overlap is reported only when a use hits both instances; merely
        declaring or importing them is fine (as Agda). Rejected (B), Lean
        style: priorities and "most recent first" with backtracking, no
        ambiguity error; it needs priority syntax, an order of instances
        across modules (B-4 tables are `Map`s), backtracking in E-3, and
        the choice would depend on declaration / import order. A way to
        prefer more specific instances (as Agda's `OVERLAPPING` pragmas)
        may be added later.
        Head arguments (I4, second half): no restriction besides renaming's
        "every type variable occurs in the head" (as Agda / Lean; Haskell
        98's `C (T a1 ... an)` is not imposed); non-terminating search is
        stopped by E-3's depth limit.
- (E-5) New `ErrorDetail` constructors (now: `UnMatchTy`, `Escape`, ...,
  `Other Doc`; `TCMonad.hs:59`):
    NoInstance Ty                    no metas, no matching candidate (E-2)
    AmbiguousInstances Ty [Name]     several globals unify with a goal
                                     without metas (E-4 (4), revised)
    AmbiguousGoal Ty                 metas left that can no longer be fixed
                                     (e.g. top-level def with sig; E-2);
                                     "add a type annotation"
    CannotInferInstArg Ty            top-level sig-less def with a
                                     polymorphic goal (E-2 (a)); "write a sig"
    InstSearchTooDeep Ty             depth limit (E-3)
    NotInstArgPosition               `{{e}}` / `{{p}}` at a `FunTy` (D-1, C-2)
    InstArgUnknownFun                `{{e}}` to a function of unknown type
                                     (D-1, A-4)
    InstPatNeedsAnnotation           `{{p}}` where the type is unknown
                                     (C-2, C-4)
    NotAClass Ty                     non-class in `{{ }}`, instance head,
                                     instance argument, superclass (Q2, G)
    ClassArityMismatch Name Int Int  wrong number of class arguments, inside
                                     or outside `{{ }}` (Q2, B-1)
    NotAMethod Name Name             a `def` in an instance body that is not
                                     a method of its class (G)
    MissingMethod Name Name          a method without default not defined (G)
  Notes:
    1. A missing superclass instance (`Eq T` for `Ord T`) is `NoInstance`
       with a new `WhenChecking` context "checking the superclasses of
       instance X" (`pprWhenChecking`).
    2. Goal errors are reported with the goal's creation context
       (`goalCtx`, E-1), pointing at the inserted application even when
       solved later.
    3. "Cannot happen" errors (`InstArg` in H-1, `Infer` in C-3) are not
       `ErrorDetail`s; plain `error "Cannot happen."` as now.
    4. Nonexamples tests only check that a `StaticException` is raised, so
       the split is for messages, not for tests.

Typed AST of inserted forms
---------------------------

- (F-1) Inserted forms use the existing constructors, except the hole
  `InstHole` of F-3 standing for a goal's dictionary.
    1. Inserted abstraction (C-1):
         Abs [Loc l (PInst (Loc l (PVar (d, c))))] e'
       `d` is `Generated i TypeChecking`, `c` the class type
       (`XId 'TypeCheck = (Name, Ty)`).
    2. Pattern inserted in a clause (C-2, `Inserted c`): the same
       `PInst (PVar (d, c))` at the corresponding position of the pattern
       list.
    3. Inserted application (D-1, D-2):
         App f (Loc l (InstArg (Loc l (InstHole ref))))
       `InstHole ref` stands for the goal and is filled after solving (F-3).
    4. Dictionary expressions built by search (E-3):
         local instance        Var (d, c)
         global instance       App (Var (inst, ty)) (InstArg sub) ...
         superclass projection App (Var (proj, ty)) (Var (d, c))
       A projection is an ordinary function (`Ord a -> Eq a`), applied
       without `InstArg`.
    5. Operators (D-3): rebuilt as `App (App (Var (op, ty)) e1') e2'`;
       inserted `InstArg`s go into this application chain.
    6. Inserted forms are not distinguished from user-written ones
       (`\{{d}} -> e`, `def f {{d}} ...`, `f {{e}}`), so desugaring (H-4)
       has a single case for each.
    7. Locations: an inserted abstraction gets the location of the
       expression it wraps; an inserted application gets the span from the
       head to that argument. Runtime errors and desugared output can then
       point at the source.
- (F-3) Filling in dictionary expressions: plan (b), a hole with an IORef.
    1. Surface.Syntax gets a type family and a constructor:
         type family XHole (p :: Pass) where
           XHole 'Parsing   = Void
           XHole 'Renaming  = Void
           XHole 'TypeCheck = IORef (Maybe (LExp 'TypeCheck))
         | InstHole !(XHole p)    -- dictionary of a goal (made by D-1 / D-2)
       Only the type checker makes it; parsing and renaming never see it
       (`absurd` / "cannot happen" in their cases).
       REVISED at stage 0 (user, 2026-11-05): `XHole` is only a tag, like
       `XOp`, and the ref is an ordinary field:
         type family XHole (p :: Pass) where
           XHole 'Parsing = Void; XHole 'Renaming = Void; XHole 'TypeCheck = ()
         | InstHole (XHole p) !(IORef (Maybe (LExp p)))
       (tag lazy, H-1 2). Printing needs no per-pass class: `Pretty (Exp p)`
       reads the ref and prints `pprPrec 10 e` or `?`.
    2. Each inserted application (D-1, D-2) creates a fresh ref, puts
       `InstArg (InstHole ref)` in the AST and records it as `goalRef` of
       the goal (E-1). When the goal is solved (E-2, E-3), the dictionary
       expression (F-1 4) is written to the ref. Subgoals of E-3 are solved
       on the spot, so dictionary expressions themselves contain no holes.
    3. Desugaring (H-4) reads the ref (`lift`, as `zonkType`) and desugars
       its contents; an empty ref is "cannot happen" (E-2 reports unsolved
       goals as errors before desugaring).
    4. Pretty printing shows the contents if filled and `?g_k` (`goalId`)
       otherwise, reading the ref by `unsafePerformIO` as metas are printed
       (`Type.hs:260`). [Stage 0 prints only `?`: the hole does not carry
       the goal's name yet. To be fixed in stage 3 when goals are made
       (user, 2026-11-05).]
    5. A goal postponed outward (E-2) needs nothing special: the ref is
       carried by the goal.
  Why: this is how meta type variables are handled. Their solutions are
  in the IORef of each `MetaTyVar` (`metaRef`, `Type.hs:249-256`), carried
  by the types in the typed AST, and desugaring reads them by `zonkType`.
  Results of type checking reach desugaring only through the output (AST,
  return values): `Module.hs` type-checks with `execTCWith`, whose
  context `tc'` (made by `refreshTC` at the start of each type-checking
  run, so that constraints and errors of one input do not leak into the
  next) is local to it, and then desugars with the outer `tc` by
  `execTC` (`Module.hs:500-507`). (That desugaring does not use `tc'` is
  a consequence of how `Module.hs` calls them, not of the refresh; it is a
  latent bug, see "TODO / known issues".) A solution table in
  `TypingContext` would therefore not be visible to desugaring.
  Rejected: (a) `Var (g_k, c)` plus substituting solutions over the whole
  typed AST at the end of `inferTopDecls` (no such traversal exists; it
  would need updating for every syntax change; H-2 must call it too);
  (c) `Var (g_k, c)` plus returning the solution table from
  `inferTopDecls` and passing it to desugaring (workable, but the typed
  AST alone would not determine the dictionaries, and goal names
  `Generated i TypeChecking` restart per input, so keys need care).
  (Running desugaring inside the same `execTCWith` would also make a table
  in `tc'` visible; not needed with (b).)

    top-level `def`.

- (H-1) Impossible cases in `checkTy` (under the expression revision (c),
  "Representation"):
    1. There is no `InstArg` case: `InstArg` is a constructor of `Arg`,
       not of `Exp`. `App f a` is handled by the spine (D-1), whose
       arguments `[Arg]` are processed from the left; `InstArg e` is the
       `Inst e` row of D-1's table. (The earlier proposal "`go (InstArg _)`
       is cannot-happen" is no longer needed.)
    2. `go (InstHole v _) = absurd v`, since `XHole 'Renaming = Void`
       (F-3; `XHole` is a tag, F-3 1 revised);
       guaranteed by the type, not a run-time "cannot happen".
       Implementation note (stage 0, 2026-11-05): the tag field is LAZY,
       `InstHole (XHole p) ...` (likewise `Op (XOp p) ...`, H-4-1 4), as the
       existing `Decls (XDecls p) ...` / `HDecls (XHDecls p) ...`. With a
       strict `!` field GHC's pattern-match checker treats the constructor
       as uninhabited where the field is `Void` and reports the `absurd`
       equation as redundant (-Woverlapping-patterns); lazy fields keep
       the explicit `absurd` cases, in the codebase's existing style
       (user's choice (ii); rejected (i): strict fields with the cases
       omitted).
    3. Patterns: with `PInst` as now (the `ArgPat` revision is on hold,
       TODO), C-3's `go (PInst p)` is used at argument positions; other
       positions and contents other than a variable / `_` are rejected by
       renaming (`checkInstPatArg` / `checkNoInstPat`), so the type checker
       does not check them. Revisit when the pattern question is decided.
- (H-2) REPL (evaluation and `:type`; both go through `readExp`,
  `Module.hs:392-433`, i.e. `inferExp` -> `inferPolyTy True`, Infer mode
  and generalization).
    1. `readExp`'s `execTCWith` also gets `mcClassTable` / `mcInstTable`
       (B-4; the same `setEnvs` extension as B-1 / B-4), otherwise goals of
       methods used in a REPL expression cannot be solved.
    2. In `inferPolyTy` the inference is wrapped by `gatherGoals` and the
       goals are solved before `generalizeTy`, as for a top-level sig-less
       definition (E-2): goals with generalizable variables are
       `CannotInferInstArg`, leftovers are errors. E.g.
       `elem 1 (Cons 1 Nil)` solves `Eq Int`; `\x -> x == x` (the body
       inserts a leading instance argument, since arguments follow) leaves
       a polymorphic `Eq ?a`, `CannotInferInstArg`.
    3. A REPL expression is in Infer mode, so its outermost spine inserts
       no trailing instance arguments (D-2 (M1)): `:type elem` shows
       `forall a. {{Eq a}} -> a -> List a -> Bool`; evaluating `elem` gives
       a function value expecting a dictionary; `:type (==) {{eqNat}}`
       shows `Nat -> Nat -> Bool`.
    4. Desugaring runs later as `eComp`; dictionaries are in the
       `InstHole` refs of the AST (F-3 (b)), so the context-sharing issue
       (TODO) does not affect it.
- (H-3) `rev` contexts (checked against `Examples-Class/Invertible.sparcl`:
  `rev` / linear method types, `rev` patterns and `with` in instance
  bodies, `# Omega` methods, a local instance used twice, `fwd` / `bwd`
  via `unlift`). No special treatment for `rev`:
    1. Dictionaries are always ordinary (non-`rev`) values: instance
       arrows are Omega (A-1), `{{rev x}}` is rejected by renaming, and
       local instances are removed from use maps (C-1, C-3), so linearity
       checking is unaffected (`twice` uses its `d` twice).
    2. Clauses with `rev` patterns align by C-2: in the body of
       `instance {{RevSucc a}} -> RevSucc (List a)`,
       `def rsucc (rev Nil) = rev Nil with isNil` against
       `{{RevSucc a}} -> rev (List a) -o rev (List a)` gives `Inserted`,
       then `Explicit`; the rest `rev (List a)` satisfies `ensureRevTy`
       (`hasPRev`) and `with`'s `expectRevTy`. An instance argument after
       the explicit ones (`... -> {{C a}} -> rev T` with `with`) is C-2's
       documented limitation (workaround `{{_}}` on the left-hand side).
    3. `fwd twice (S Z)`: `twice` is checked against `rev ?a -o rev ?b`

    4. Evaluation: applying / projecting dictionaries is static (forward)
       computation, evaluated alike in both directions of `unlift`; a
       projected method is used in `rev` code like a global function

       [Confirmed at stage 5: `t1` .. `t9` give the expected values

       No effect now (constructors take no instance arguments, D-4); with
       constructor instance arguments in the future (TODO),
       `MkT : {{Eq a}} -> a -> T a` would expand to
       `\d x -> Con MkT [d, x]`, keeping the dictionary as a field. Notes
       in A-2 and C-2 corrected.
- (H-4-2) Dictionary representation: plan (a), a dedicated constructor
  per class.
    - Fields: superclass dictionaries in `extends` order, then methods in
      sig order (`ciMethods`); with m superclasses, superclass i is field
      i and method j field m + j. E.g. `class Ord a extends Eq a` with
      `compare`: `[Eq dictionary, compare]`.
    - Value: `C.Con dictC [f1, ..., fn]` with a new System name `dictC`
      (naming in H-4-3); projection by
      `\d -> case d of dictC x1 ... xn -> xi` (Core `Case` / `PCon`).
    - A class without superclasses and methods has `C.Con dictC []`; a
      single-method class has the same shape (no newtype-like special
      case).
    - Why (a): dictionaries are Sparcl values (Q1: `def d = eqNat`) and
      may be printed in the REPL, so showing the class helps; `Con` /
      `Case` in the evaluator only compare constructor names, so a
      constructor without a data declaration works; `Case` is Core's own
      way of projecting.
    - Rejected: (b) Core `WTup` / `WProj i n` (no new names, direct
      projection, but reuses the construct for additive `&`-tuples,
      `WProj` has a "too loose" FIXME, printed as `&(...)`); (c) ordinary
      tuples (indistinguishable from user tuples, no advantage over (a)).
- (H-4-3) Values of methods and superclass projections; generated names.
    Found: unnamed instances are `Original currentModule (System
    (NInstance k)) ...` (`Renaming.hs:475`, `Name.hs:35`); `Original`
    names are equal iff module and `NameBase` are (`Name.hs:68`).
    1. New `SystemName`s, used as `Original m (System ...)` with `m` the
       module declaring the class:
         NDict !NameBase            dictionary constructor of class C
                                    (H-4-2)                    <dict Eq>
         NSuperProj !NameBase !Int  projection of the i-th superclass
                                    of C (E-3)                 <super Ord #0>
         NDefault !NameBase         default method of method m
                                    (G-5)                      <default />=>
       `NameBase` rather than `Name` avoids a recursive type between
       `SystemName` and `Name`; module `m` plus the base identifies the
       class / method (method names are unique top-level names in the
       module, Renaming (a)). Using the class's module makes dictionary
       expressions built in importing modules (E-3 projections) refer to
       the same names.
    2. Method j of class C (m superclasses, n fields): binding
         (the method's own name, its global type (B-5),
          \d -> case d of dictC x1 ... xn -> x(m+j))
    3. Superclass projection: binding
         (proj_{C,i} = NSuperProj C i, forall as. C as -> Si (ordinary
          arrow, Omega), \d -> case d of dictC x1 ... xn -> xi)
    4. `d`, `x1 ... xn` are `Generated i Desugaring` by `withNewNames`.
    5. Only for classes declared in the module; imported classes' methods
       and projections are in their modules' value tables (H-4-5).
    6. `case` is Core's ordinary `Case` (not `RCase`), static (H-3 4);
       fields are built lazily (G-5), so projecting one field does not
       evaluate the others.
- (H-4-4) Instance values and default-method values. Input from type
  checking (G-1 6): superclass dictionary expressions in terms of
  `d1 ... dk` (G-3 3), typed bodies of defined methods (G-5 3), omitted
  methods.
    1. `instance x : forall as. {{H1}} -> ... -> {{Hk}} -> C ts`:
         x = \d1 ... dk ->
               let self = dictC [sup_1, ..., sup_m, impl_1, ..., impl_n]
               in self
       - `d1 ... dk`: the names given in G-3 3 (`Generated i
         TypeChecking`), used as binders, since the superclass expressions
         refer to them;
       - `sup_i`: G-3 3's dictionary expression desugared (e.g.
         `eqList (proj_{Ord,0} d1)` for `ordList`);
       - defined method: `body_j d1 ... dk`, the desugared body applied to
         the dictionaries (its type is `{{H1}} -> ... -> {{Hk}} -> t[ts]`,
         so by C-1 / C-2 it takes the k dictionaries first);
       - omitted method with a default: `dflt_m self` (`NDefault m`
         applied to the instance's own dictionary, G-5 2);
       - `let self` lets the dictionary refer to itself; Core `Let` is
         recursive (`evalUBind`'s `rec`) and fields are lazy (G-5); the
         same shape also for k = 0 (instead of referring to the global x);
       - binding type: the instance type.
    2. Default method: binding `(NDefault m, forall as bs. {{C as}} -> t,
       desugarRHS of the default's clauses)`, a function taking the
       dictionary first (C-1 / C-2); only for classes declared in the
       module; imported defaults are found in the declaring module's
       value table (hence the class's module in the name, H-4-3).
    3. With k > 0 every use `x d1 ... dk` builds a new dictionary, as
       Haskell's dictionary functions; no sharing optimization.
    4. Example (`(/=)` uses the default):
         eqNat  = let self = dictEq [eqNat_eq, <default />=> self] in self
         eqList = \d1 -> let self = dictEq [eqList_eq d1,
                                             <default />=> self] in self
- (H-4-5) Top level and module value tables (decided 2026-11-05).
  Found (`Module.hs:454-571`): `interpDecls` evaluates the bindings from
  `desugarTopDecls` by `interp valEnv bind` as one recursive group and
  stores them in `mcValueTable`; `mcTypeTable` is `nts`; import / export
  lists filter all tables by names (`restrictNames` / `exportNames`);
  without an export list a module exports its own definitions only.
    1. The bindings of methods and projections (H-4-3) and of defaults and
       instances (H-4-4) are added to the result of `desugarTopDecls` and
       evaluated in the same recursive group as the `def`s, so `def`s and
       instance bodies may refer to each other (G-1 5) and dictionaries
       to themselves (G-5).
    2. `nts` also gets the types of methods, instance names, projections
       and defaults (extends B-4 (1)); the same types as in the bindings.
    3. Value tables (settles B-4 (4)): `restrictNames` / `exportNames` keep,
       besides the listed names, every name in the module's instance table
       (named and unnamed) and every `NSuperProj` / `NDefault` name, since
       expressions made by search / desugaring refer to them without the
       user writing them (instances and projections from E-3 dictionary
       expressions; defaults from instance values in other modules, e.g.
       an instance in B using the default `(/=)` of class `Eq` in A).
       Method names are user names and filtered as before (defaults and
       instance values are closures over the environment of their own
       module, so filtering methods in an importing module does not
       matter). The name table is filtered as before (whether `eqNat` can
       be written, B-4 (2)); type tables are filtered as before (search
       takes types from the instance and class tables).
    4. Transitive, as B-4 (3): the value table of a new module is its own
       values plus the values of the names kept by 3 from all imported
       modules, with or without an export list (C importing only B, which
       imports A, has A's instances in its instance table and needs their
       values). `Original` names include the module, so merging never
       clashes.
    5. Dictionary constructors (`NDict`) are not values; they are only
       names in Core `Con` / `Case`.
    6. REPL expressions are evaluated with the context's value table
       (`valueOfExpressionStr`), which has instances, projections and
       defaults by 3 and 4.
